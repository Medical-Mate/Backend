# 설계 결정을 노션에 기록

## 언제 쓰나

**되돌리는 데 비용이 드는 선택을 확정했을 때.** 구체적으로:

- 라이브러리·프레임워크·DB 채택
- 스키마 구조, 컬럼을 두거나 두지 않기로 한 판단
- 인증 방식, 외부 서비스 연동 형태
- 저장하지 않기로 한 데이터 (개인정보 관련 판단은 특히 중요)
- 범위에서 빼기로 한 기능

**쓰지 않는 경우:** 변수명, 메서드 분리, 되돌리는 데 5분이면 되는 것. 코드를 읽으면 알 수 있는 것. 로그가 길어지면 아무도 안 읽는다.

**아직 안 정해졌으면** 상태를 `재검토 필요`로 두고 지금 기록한다. "무엇을 기다리는지"가 재검토 트리거에 들어간다. 결정이 안 난 것도 기록할 가치가 있다.

## 절차

### 1. 중복 확인

`notion-query-data-sources`로 같은 주제의 행이 있는지 먼저 본다. 있으면 새로 만들지 말고 `notion-update-page`로 갱신한다. 결정을 뒤집는 경우 기존 행의 상태를 `폐기`로 바꾸고 새 행을 만들되, 새 행의 선택 근거에 무엇을 뒤집었는지 적는다.

### 2. 행 생성

`notion-create-pages`에 `data_source_id`를 부모로 넘긴다.

| 속성 | 값 |
| --- | --- |
| `결정` | 무엇을 정했는지 한 줄. 명사구로. 예: `ddl-auto: update 로 시작 (Flyway 보류)` |
| `date:날짜:start` | 결정한 날 (`YYYY-MM-DD`) |
| `영역` | `코드 구조` `데이터` `인증` `AI 연동` `API` `보안·개인정보` `인프라·배포` `프로세스` 중 하나 |
| `상태` | `확정` `잠정` `재검토 필요` `폐기` 중 하나 |
| `검토한 대안` | 고려했다가 택하지 않은 것들. `/`로 구분 |
| `선택 근거` | 아래 작성 기준 참고 |
| `재검토 트리거` | 다시 봐야 하는 조건. 없으면 `없음` |
| `관련 링크` | 이슈 또는 PR URL |

### 3. 이슈에도 남긴다

작업 이슈가 열려 있으면 그 이슈의 **비교한 대안**과 **재검토 트리거** 섹션도 같이 채운다. 노션은 프로젝트 전체 로그이고, 이슈는 그 작업의 맥락이다.

## 선택 근거 작성 기준

**일반론을 쓰지 않는다.** "성능이 좋아서", "널리 쓰여서"는 근거가 아니다. 이 프로젝트의 제약에 비춰 쓴다.

제약은 넷이다 — **3주 일정 · 백엔드 1인 · 민감정보(증상·복용약·알레르기) · 공모전 데모**.

나쁜 예:
> PostgreSQL이 JSON 지원이 좋아서

좋은 예:
> 브리핑 카드 필드가 확정 전이라 jsonb로 두면 필드가 바뀔 때마다 마이그레이션을 새로 만들지 않아도 된다.

**무엇을 포기했는지도 쓴다.** 트레이드오프가 없는 선택은 대체로 결정이 아니다.

## 재검토 트리거 작성 기준

"나중에"가 아니라 **관찰 가능한 조건**으로 쓴다.

나쁜 예: `나중에 필요하면 Flyway로 전환`

좋은 예: `카드 스키마가 확정되고 엔티티가 3개 이상 안정되면. 늦어도 2주차 시작 전.`

시한이 없으면 그대로 굳는다. 날짜나 횟수를 넣을 수 있으면 넣는다.

## 기록 후

한 줄로 보고한다. 노션 페이지 URL을 함께 준다. 결정 내용을 다시 길게 늘어놓지 않는다.
